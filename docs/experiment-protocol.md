# キャッシュ戦略の比較実験手順

## 初期キャッシュ状態

| 状態 | 定義 |
| --- | --- |
| Cold | 実験用キャッシュが存在しない |
| Fresh | 保存からの経過時間が許容鮮度の50% |
| Expired | 保存からの経過時間が許容鮮度の150% |

| API | 許容鮮度（秒） | Fresh（秒） | Expired（秒） |
| --- | ---: | ---: | ---: |
| emergency | 60 | 30 | 90 |
| important | 600 | 300 | 900 |
| articles | 1800 | 900 | 2700 |
| static-info | 86400 | 43200 | 129600 |

許容鮮度は実験用の固定値。経過時間は記事の更新日時ではなく、キャッシュの保存時刻を基準とする。

## 初期化と測定

1. モックAPIとViteを起動し、Service Workerが画面を制御している状態にする。同じオリジンの他のタブは閉じる。
2. API、戦略、通信条件、初期キャッシュ状態、シード（`seed`）、試行番号（`trialId`）を設定する。比較する各戦略で同じシードと試行番号を指定し、次の試行では試行番号を変更する。詳細を測定するときは、先に対象の一覧を表示して記事をクリックできる状態にする。一覧表示のための取得は測定対象から除外する。
3. 「キャッシュを初期化」を押し、選択した条件で初期化完了が表示されるまで待つ。失敗した場合は測定せず、原因を取り除いて初期化をやり直す。
4. 完了表示後すぐに、一覧なら「ニュースを取得」、詳細なら表示済みの記事ボタンを押す。各測定の直前に初期化を繰り返す。戦略を切り替える場合も同じ手順で初期化する。
5. ページを閉じるか再読み込みする前に「実験ログをCSVで保存」を押す。初期状態が空欄の行は、初期化条件を付与した試行の集計から除外する。

Service Workerは `news-api-cache-v1` を削除する。FreshとExpiredではモックAPIの `normal` 条件から一覧と各記事の詳細を取得し、同じ人工保存時刻を `X-Cache-Saved-At` に記録する。キャッシュキーには実験で選択した通信条件を使う。たとえば `/api/emergency?condition=severe` と `/api/emergency/news-001?condition=severe` は別のキーであり、`condition=normal` のキーとも区別される。戦略間で同じキーを共有する。

初期化そのものはログに記録しない。選択条件に一致するキーごとに、初期化後の最初の取得へ `initialCacheState` と `configuredAgeSec` を付ける。Coldの設定経過秒数は空欄。実測の `cacheAgeSec` には、初期化後の待ち時間や取得中の経過時間が含まれる。

## 指標と集計対象

- 表示時間は取得操作開始から最終DOM更新までの `durationMs`。画面に記事を表示できた成功試行で集計する。
- 取得成功率は成功件数 ÷（成功件数＋失敗件数）。キャッシュへのフォールバックで表示できた試行も成功に含める。
- 鮮度違反率は成功試行のうち、`stalenessViolation=true` の件数 ÷ 判定可能な成功件数。表示したキャッシュの実際の経過時間が許容鮮度を超えると違反になる。ネットワーク成功は違反なし。判定不明は分母から除外して件数を併記する。
- 失敗は成功率の分母に含める。表示前に選択変更などで破棄された試行は3指標から除外し、件数を別途記録する。集計の分母が0なら該当指標は算出しない。

## 通信条件と再現性

| 条件 | モック遅延 | 失敗率 |
| --- | --- | ---: |
| normal | 100 ms | 0% |
| mild | 1000 ms | 10% |
| severe | 3000 ms | 30% |
| unstable | 100〜5000 ms | 30% |

画面は `X-Experiment-Seed` と `X-Experiment-Trial-Id` を送る。省略時の値はどちらも `1`。Service Workerはネットワーク取得時に両ヘッダーを転送する。キャッシュキーは従来どおりパスと `condition` クエリで決まる。取得開始時の値はログとCSVの末尾2列に記録する。

モックAPIはシード、試行番号、リクエストパス（詳細は記事IDを含む）、通信条件の組み合わせをSHA-256でハッシュ化する。先頭の4バイトから設定遅延を、次の4バイトから失敗判定を求める。各リクエストの結果は前のリクエストから独立して決まり、戦略名は入力に含まれない。失敗率は試行ごとの判定閾値で、一定件数ごとに失敗数を割り当てる方式ではない。ネットワーク応答の `X-Simulated-Delay-Ms` で設定遅延を確認できる。実測の表示時間には通信と画面処理の時間も含まれる。

### 再現性の確認（2026-11-27）

- 実HTTPで6通りの要求を送り、戦略ヘッダーを変更し、要求の送信順を逆にして無関係な要求を1件加えても、HTTPステータスと設定遅延が6通りすべて一致した。Emergency一覧・シード `7` では unstable の試行 `1` がHTTP 200／3228 ms、試行 `4` がHTTP 503／1212 ms。severe の試行 `1` はHTTP 200、試行 `9` はHTTP 503で、いずれも3000 msだった。
- Node上のService Worker模擬環境を実HTTPに接続し、Coldの3戦略で同じ503と設定遅延を確認した。Freshではシードと試行番号を変えても一覧・詳細のキャッシュを利用でき、Expiredでは503時に警告付きフォールバックを確認した。ログとCSV文字列に試行値が入り、CSVの既存列順も維持された。実ブラウザーでのダウンロード確認は保留。

端末、ブラウザーとバージョン、コードの版、記事データ、API種別、一覧・詳細の区別、通信条件、初期化から計測開始までのタイミングをそろえる。ブラウザー側のスロットリング設定も統一する。試行回数、試行順序、初期化完了から開始までの許容時間は結果を見る前に確定する。
